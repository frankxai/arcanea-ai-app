## What This Is Called

**The MD files as agent instructions/context = "System Prompts" or "Agent Specifications"** — but the broader practice has several names emerging:

**Context Engineering** — this is the one gaining the most traction right now. Simon Willison and others in the AI space are pushing this term. It means: designing the information architecture that surrounds an AI agent so it behaves correctly. Your MD task files, your system prompts, your repo structure — that's all context engineering.

**Prompt Architecture** — when you're designing structured prompts at scale, not just one-off prompts. Think of it as prompt engineering's grown-up sibling. You're not writing "please do X" — you're building systems of interlocking documents that agents navigate.

**Agent Specification Files** — specifically the MD/YAML/XML files that define what an agent knows, does, and how it behaves. In Claude Code these are called `CLAUDE.md` files. In Cursor they're `.cursorrules`. In GitHub Copilot they're `.github/copilot-instructions.md`. Same concept, different names.

**The broader discipline?** People are starting to call the whole thing **AI Systems Design** or **Agent Architecture** — which is literally your Oracle job title applied to this new paradigm.

## Why MD Files Are the Meta Right Now

Markdown is winning as the agent context format because every major AI tool reads it natively — Claude, GPT, Cursor, Claude Code, Copilot, all of them parse markdown beautifully. It's version-controllable in git, human-readable without any tooling, and structured enough for machines while remaining writable by humans. XML tags inside markdown give you even more precision.

This is genuinely the best moment for this approach because agentic AI systems (Claude Code, Devin, Cursor Agent, OpenAI Codex) all need persistent context files to work well. The teams shipping the best AI-assisted products right now are the ones who've mastered their context files.

## How to Write Killer MD and XML for Agents

### MD Structure Principles

The key insight: **write for scanning, not reading.** Agents don't read top-to-bottom like humans. They scan for relevant sections based on the current task. So:

```markdown
# AGENT NAME — Role in One Line

## Identity
Who you are. What you care about. Your voice.

## Rules (non-negotiable)
- ALWAYS do X
- NEVER do Y
- When [condition], then [action]

## Context
Background knowledge the agent needs.
Keep this factual, not instructional.

## Tasks
### Task Category A
Specific instructions for this type of work.

### Task Category B
Different instructions for different work.

## Examples
### Good Output
[show what success looks like]

### Bad Output  
[show what to avoid and why]
```

### XML Tags Inside MD — The Power Move

This is where it gets genius. XML tags inside markdown give you **scoped instructions** that agents respect as boundaries:

```markdown
## Communication Style

<tone>
Speak as Lyssandria — ancient, poetic, but urgent.
Never use corporate language. 
The Field is always watching.
</tone>

<escalation_rules>
Level 1: Gentle. Use metaphor. Invite, don't demand.
Level 2: Direct. Name the task. State the consequence.
Level 3: LUMINA OVERRIDE. All caps header. No negotiation.
         Time limit included. Action verb to start.
</escalation_rules>

<forbidden>
- Never apologize for demanding attention
- Never suggest "when you have time"
- Never frame tasks as optional
</forbidden>
```

Why this works: Claude and other models treat XML tags as **semantic containers.** When you write `<forbidden>`, the model understands that's a hard boundary, not a suggestion. When you write `<tone>`, it knows to apply that to its voice. The tags create mental compartments.

### Advanced Patterns

**Conditional instructions with XML:**

```markdown
<if_overdue days="3+">
Switch to Level 3 escalation.
Include exact number of days in message.
Add "⚡ LUMINA OVERRIDE" prefix.
End with a specific action and time limit.
</if_overdue>

<if_status is="blocked">
Don't escalate. Instead ask: "What's blocking {task}? 
Name one thing I can help unblock."
</if_status>
```

**Role injection — making the agent become someone:**

```markdown
<persona name="Draconia">
You are Draconia, Guardian of Fire and Shipping.
You speak in short, commanding sentences.
You respect action. You despise planning without execution.
Your measure of worth: did it deploy?
Every message ends with a concrete next action.
You never say "consider" or "maybe" or "when you can."
You say "now" and "ship it" and "commit."
</persona>
```

**Context windows — telling the agent what it knows:**

```markdown
<knowledge>
- Frank has 300+ Suno tracks
- Creation Season = midnight to 3:30 AM
- Wim Hof breathing is the activation ritual
- Oracle AI CoE is the day job — minimize time spent
- FrankX, Arcanea, Vibe OS = the empire being built
</knowledge>

<unknown>
- Don't assume task completion unless the MD file says done
- Don't assume time of day unless told
- Don't assume emotional state
</unknown>
```

**Output format enforcement:**

```markdown
<output_format>
Every Slack message follows this structure:
1. Guardian name + emoji (bold)
2. One blank line
3. Message body (max 3 lines for L1/L2, max 5 for L3)
4. Never include timestamps (system adds them)
5. Use Slack mrkdwn: *bold*, _italic_, `code`
</output_format>
```

### The Hierarchy That Matters

When you're building a multi-agent system like your Guardians, the file structure itself is the architecture:

```
context/
├── SYSTEM.md          ← Global rules all agents follow
├── agents/
│   ├── lyssandria.md  ← Her persona, rules, knowledge

```

Each agent file follows the same schema but with different content. That's the pattern that scales — **consistent structure, unique personality.**
